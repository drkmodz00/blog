The "Speed vs. Security" Trap: Lessons from a 72-Hour Breach

edit_document Editorial Team
October 26, 2023
8 min read

In the modern development landscape, "moving fast and breaking things" is often celebrated as the hallmark of innovation. At a recent university hackathon, three students took this to heart, leveraging AI coding assistants to build a membership and payment platform for student organizations in under 72 hours. It worked. It won a prize. It gained users.

Then it collapsed.

Word spread fast. Within a month, more than a dozen student organizations had adopted the app, and it was quietly holding real, sensitive data: full names, student numbers, phone numbers, GCash reference screenshots, uploaded ID photos, and private group chats. What began as a weekend demo had become production software for hundreds of students, without ever being treated like production software.

The exposure wasn't found by an attacker. It was found by a member who noticed that changing the number at the end of a profile link — from /profile/1048 to /profile/1049 — loaded a complete stranger's record: student number, contact details, and the photo of their uploaded ID. Curiosity led that same student to the project's public GitHub repository, where the database password and a payment API key were sitting in plain text inside an early commit. This post explores the technical debt that led to this exposure, the Secure Design Principles that were ignored, and how to rebuild such a system the "right way."

The Anatomy of the Failure

The platform suffered from several classic vulnerabilities that, while easy to implement for speed, are catastrophic in production:

vpn_key_alert

Insecure Direct Object References (IDOR)

Changing a URL parameter allowed users to view sensitive records of other students.

password

Hardcoded Credentials

Database passwords and API keys were committed in plain text to a public GitHub repository.

gpp_bad

Broken Access Control

Every account was provisioned with broad database read access.

leak_add

Information Leakage

Detailed error pages (stack traces) were visible to any user.

wifi_off

No Transport Encryption

The whole system ran over plain HTTP on a free hosting tier — IDs, phone numbers, and payment screenshots traveled unencrypted.

visibility_off

Security by Obscurity

The team assumed that because nobody knew the internal URL structure, nobody would go looking. No real access control backed that assumption up.

Violated Secure Design Principles

  • check_circle
    Least Privilege: every account and database connection was provisioned with broad read access it never needed. A student's login had no business being able to query rows belonging to other students, but the system never distinguished between "authenticated" and "authorized."
  • layers
    Defense in Depth: there was exactly one layer standing between a stranger and hundreds of ID photos — an unguessable-looking number in a URL. When that one layer failed, nothing else caught the fall.
  • block
    Fail-Safe Defaults: the system's default behavior on an unrecognized or unverified request was to serve the data anyway. A secure default denies access until ownership is proven; this one granted it until someone objected.
  • rule
    Complete Mediation: every single request for a protected object should be checked, every time, with no exceptions. The /profile/:id endpoint checked whether a user was logged in, but never whether the logged-in user was allowed to see that specific record.
  • visibility_off
    Open Design: security should never depend on attackers not knowing how the system works. Treating the URL structure as a secret, rather than building real authorization behind it, is the textbook violation of this principle — and it's exactly what "security by obscurity" means in practice.

Horizon 1: The Immediate Containment (Hours to Days)

When a faculty adviser was shown the URL trick, the app was pulled offline. This was the correct first step. Here is the immediate tactical response required to stabilize the situation — dense, urgent, and sequenced by how fast the exposure can keep growing if left alone:

power_settings_newHour 0

Take the System Offline and Freeze New Signups

Restores: Fail-Safe Defaults

This is what the faculty adviser correctly did the same afternoon. Every hour the app stays reachable, the sequential-ID scan can keep running. The default state while the system is untrusted has to be "off," not "on until proven dangerous."

key_offHour 0–2

Revoke and Rotate All Secrets

Restores: Secure Secrets Management

The database password and the GCash payment API key found in the GitHub commit history are compromised forever, even after the commit is deleted, because git history is trivially recoverable. Generate new credentials for every service and store them in environment variables, never in source control.

verified_userDay 1

Patch the IDOR With a Real Ownership Check

Restores: Complete Mediation

Before the app goes back online, every route that reads or writes a record must confirm the requesting user actually owns — or is explicitly permitted to view — that record, not just that they're logged in. A single shared authorization middleware, applied to every data route without exception, closes the door the URL-swap trick walked through.

bug_reportDay 1

Turn Off Verbose Errors in Production

Restores: Least Privilege / Information Hiding

Stack traces are a debugging convenience, not a public feature. Replace them with a generic error message for users, and route the real detail to a private, access-controlled log instead — a stack trace tells an attacker exactly which framework, file paths, and query structure to target next.

encryptedDay 1–2

Force TLS and Reset User Sessions

Restores: Confidentiality in Transit

Most free hosting tiers offer HTTPS with a single configuration flag — there is no excuse for launching without it. Invalidate all existing sessions so the relaunch starts from a clean slate rather than trusting cookies issued under the old, unencrypted setup.

campaignDay 2–3

Notify Affected Students — and the NPC

Legal Obligation: RA 10173 Breach Notification

Under the Data Privacy Act and NPC Circular 16-03, a personal information controller must notify both the National Privacy Commission and affected data subjects when a breach is likely to give rise to real risk of serious harm — generally within 72 hours of learning about it. Sensitive personal information (IDs, contact details) and financial data (GCash records) both clear that bar. Silence isn't a neutral option here; it's a separate violation on top of the breach itself.

Horizon 2: Rebuilding the Right Way (Long-term Design)

Restoring the app isn't just about patching bugs; it's about a structural shift in how data is handled. These changes are slower and quieter than Horizon 1's triage, but they're what actually keeps the next IDOR, the next leaked key, and the next silent HTTP request from happening again.

Authorization as a Layer, Not a Habit

Restores: Complete Mediation

Move ownership checks out of individual route handlers and into a single, shared authorization layer every request passes through. When the check lives in one place instead of being re-implemented (or forgotten) per endpoint, one missed if statement can't reopen the same hole.

Scoped, Least-Privilege Database Roles

Restores: Least Privilege

Replace the single superuser connection string with narrow service accounts — a read-only role for reporting, a scoped write role for the app server — so that even a fully leaked credential can't hand over the entire database.

Secrets Stay Out of Git, Structurally

Restores: Secure Secrets Management

Pair environment-variable secrets with a pre-commit hook (tools like gitleaks or git-secrets) that scans every commit for credential-shaped strings and blocks it before it ever reaches GitHub — turning "don't hardcode secrets" from a rule people can forget into a rule the tooling enforces.

Monitoring for the Next Sequential Scan

Restores: Defense in Depth

Structured logging and basic anomaly alerts — one account requesting a thousand sequential profile IDs in a minute, for instance — give the team a second layer that catches what authorization checks miss, instead of relying on a curious student to notice by accident.

Store Less, Encrypt What Remains

Restores: Data Minimization

Does the app need to keep raw ID photos and GCash screenshots indefinitely, or only long enough to verify a payment? Purge what's no longer needed, encrypt what must be retained at rest, and treat every stored field as a liability the org has to justify keeping — not a free byproduct of collecting it once.

Auditing What the AI Actually Wrote

The team's mistake wasn't using an AI coding assistant — it was trusting its output the way you'd trust a senior engineer's. An AI assistant optimizes for whatever it was asked to do: "build a membership and payment platform" produces working CRUD routes, a working login flow, working file uploads. Nothing in that prompt asked for object-level authorization on every route, so the model didn't add it. Nothing asked for scoped database roles, so it defaulted to one connection string with broad access, because that's what makes a demo run in 72 hours. The code was plausible, it compiled, it passed the happy-path test of "does clicking around work" — and it still shipped every one of the failures above.

The fix is a review step scoped specifically to what AI-generated code tends to skip: does every data-returning route check ownership, not just login state? Are credentials externalized? Do error handlers fail generically in production? Is there a rate limit or anomaly check on anything sequential or enumerable? Treat AI output as a fast first draft from a contractor who has no stake in the consequences — useful, often correct, and never a substitute for a human threat-modeling the result before it touches real students' data.

gavel

The Ethical and Legal Mandate

As developers in the Philippines, we operate under Republic Act No. 10173, also known as the Data Privacy Act of 2012 (DPA).

Under the DPA, developers and organizations have a legal obligation to implement "reasonable and appropriate organizational, physical, and technical measures intended for the protection of personal information." That obligation doesn't pause for a hackathon deadline, and it doesn't transfer away because the code was AI-generated or the hosting was free. The three students, as the people who designed the system's access rules, are the ones the law treats as accountable for whether student data stayed protected — the org that adopted the app for membership dues shares that accountability the moment it collects a member's ID photo through it.

The DPA's Accountability principle means responsibility follows the data, not the org chart — you don't get to outsource it to "the AI wrote that part." Its Proportionality and data-minimization principles are exactly what should have stopped indefinite storage of raw ID photos and GCash screenshots in the first place. And its breach-notification rule under NPC Circular 16-03 is not optional paperwork; it's the mechanism that lets affected students actually protect themselves — watch for identity misuse, cancel a payment, change a password — instead of finding out secondhand.

Conclusion: Shipping Fast vs. Shipping Right

The "72-hour prototype" is a great learning tool, but it is rarely production-ready. We must weigh the desire to "ship fast" against the fundamental right to privacy of the people whose data we hold. A prize at a hackathon measures whether something works over a weekend; it says nothing about whether it's safe to hand to a dozen student organizations a month later.

In the age of AI, the barrier to entry for coding has dropped, but the responsibility for the consequences of that code has never been higher. An assistant will happily generate an endpoint that logs a user in, stores a payment screenshot, and returns a profile by ID — all correctly, by the definition of "does it run." Whether that endpoint checks who's asking, whether that screenshot is encrypted, whether that ID lookup is authorized — that's a design decision no prompt makes for you. It's the developer's, every time, and under RA 10173 it's a legal one as much as a technical one. A system that "runs" but exposes its users isn't a success; it's a liability, and increasingly, it's a breach the law expects you to have prevented.
